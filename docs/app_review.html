Sicherheitsanalyse & Hardening-Anforderungen

1. Bypassing der Benutzer-Eigentümerschaft (ID-Spoofing / Broken Object Level Authorization)
src/users/users.controller.ts
GELÖST
Status (29.07.2026): Behoben via verifyUserOwnershipOrSuperAdmin() in src/users/users.controller.ts. Alle mutierenden User-Endpunkte prüfen jetzt req.user.uid === :id oder super_admin-Rolle.

Mehrere Endpunkte in UsersController (z.B. PATCH /users/:id/profile, DELETE /users/:id/profile, POST /users/:id/profile/picture, POST /users/:id/blocked-users) prüfen nicht, ob die ID in der URL mit der ID des authentifizierten Benutzers (req.user.uid aus dem Firebase-JWT) übereinstimmt! Jeder authentifizierte Benutzer (auch ein anonymer App-Benutzer) kann die ID eines fremden Benutzers senden und dessen Profil, Profilbild oder Sperrliste ändern oder löschen.
// VULNERABLE (Aktuell): @Patch(':id/profile') public async updateProfile(@Param('id') id: string, @Body() dto: Partial) { return this.usersService.update(id, dto); // Keine Prüfung ob req.user.uid === id! } // GEHÄRTET (Empfehlung): @Patch(':id/profile') @UseGuards(AuthGuard) public async updateProfile(@Request() req: any, @Param('id') id: string, @Body() dto: Partial) { if (req.user.uid !== id && req.user.userType !== 'super_admin') { throw new UnauthorizedException('Sie dürfen nur Ihr eigenes Profil bearbeiten'); } return this.usersService.update(id, dto); }
2. Vertrauen in URL-Pfad-Parameter für Rollenprüfungen
src/users/users.controller.ts (Zeile 300)
GELÖST
Status (29.07.2026): Behoben via @UseGuards(RolesGuard) und @Roles('super_admin') auf GET /users/:userId/business-users. Autorisierung basiert jetzt auf dem JWT, nicht auf URL-Parametern.

Der Endpunkt getAllBusinessUsers(@Param('userId') userId: string) prüft die Autorisierung, indem er das Profil des übergebenen userId aus der Datenbank lädt. Wenn ein Angreifer eine bekannte Super-Admin-ID in die URL einfügt, lädt das Backend das Super-Admin-Profil, sieht userType === SUPER_ADMIN und gewährt dem Angreifer Zugriff auf alle Business-User-Daten!
// VULNERABLE (Aktuell): public async getAllBusinessUsers(@Param('userId') userId: string) { const requestingUser = await this.usersService.getUserProfile(userId); // Liest ID aus URL! if (!requestingUser || requestingUser.userType !== UserType.SUPER_ADMIN) { throw new UnauthorizedException('...'); } return this.usersService.getAllBusinessUsers(); } // GEHÄRTET (Empfehlung): @Get('business-users/all') @UseGuards(RolesGuard) @Roles('super_admin') public async getAllBusinessUsers() { return this.usersService.getAllBusinessUsers(); // Nutzt req.user aus vertrauenswürdigem JWT Token! }

src/businesses/application/controllers/businesses.controller.ts
GELÖST
Status (29.07.2026): Behoben via @UseGuards(RolesGuard), @Roles('business_user', 'super_admin') und verifyBusinessAccessOrSuperAdmin() in src/businesses/application/controllers/businesses.controller.ts.

4. Mass Assignment Risiko durch fehlende ValidationPipe-Optionen
src/main.ts (Zeile 92)
GELÖST
Status (29.07.2026): Behoben in src/main.ts mit whitelist: true, forbidNonWhitelisted: true und transform: true.

5. Pfad-Extraktionsfehler in FirebaseStorageService.deleteFile()
src/firebase/firebase-storage.service.ts (Zeile 66)
GELÖST
Status (29.07.2026): Behoben in src/firebase/firebase-storage.service.ts. Pfad-Extraktion nutzt jetzt urlParts.slice(domainIndex + 2) statt + 1, sodass der Bucket-Name nicht mehr im Pfad enthalten ist. Tests in firebase-storage.service.spec.ts.

Beim Löschen von Dateien aus Google Storage URLs wird der Pfad mit urlParts.slice(bucketIndex + 1) extrahiert. Bei Standard-Storage-URLs bleibt dadurch der Bucket-Name im Pfad enthalten (z.B. bucket-name/images/logo.png), wodurch der Löschbefehl im Bucket nach einem Ordner mit dem Namen des Buckets sucht und fehlschlägt.

NestJS Architektur & Best Practice Optimierungen

1. Unvollständige Exception Filter Abdeckung (@Catch Scope)
src/core/filters/http-exception.filter.ts
GELÖST
Status (29.07.2026): Behoben in src/core/filters/http-exception.filter.ts. Filter nutzt jetzt @Catch() ohne Typ-Einschränkung und fängt alle Exceptions ab. Unerwartete 500er-Fehler werden geloggt, Stack-Traces nicht an Clients geleakt. Tests in http-exception.filter.spec.ts.

HttpExceptionFilter ist mit @Catch(HttpException) annotiert. Unerwartete Runtime-Fehler (z.B. TypeError, NullPointer, Datenbank-Verbindungsabbruch) erben nicht von HttpException. Sie fallen auf den Standard-Express-Error-Handler zurück, was zu uneinheitlichen HTML-Fehlerantworten, fehlendem strukturieren Logger-Output und potentiellem Stack-Trace-Leakage führen kann.
// Empfohlene Lösung: All-Exceptions Filter @Catch() // Fängt ALLE Fehler ab export class AllExceptionsFilter implements ExceptionFilter { private readonly logger = new Logger(AllExceptionsFilter.name); catch(exception: unknown, host: ArgumentsHost) { const ctx = host.switchToHttp(); const response = ctx.getResponse(); const status = exception instanceof HttpException ? exception.getStatus() : HttpStatus.INTERNAL_SERVER_ERROR; if (status === 500) { this.logger.error('Unhandled Internal Server Error', exception); } response.status(status).json({ statusCode: status, timestamp: DateTimeUtils.getBerlinTime(), message: status === 500 ? 'Internal server error' : (exception as any).message, }); } }
2. In-Memory Cache Isolation & Multi-Replika Skalierung
src/core/cache/cache.config.ts & AppModule
INFO
Das Caching nutzt aktuell einen In-Memory LRU-Cache pro Node.js-Prozess/Docker-Container. Wenn das Backend auf dem VPS mit mehreren Repliken/Instanzen skaliert wird, entsteht ein Split-Brain-Cache (Änderungen in Container A sind in Container B nicht bekannt). Gemäß ../CONSTITUTION.md#3-konfiguration ist die Migration zu Redis als verteiltem Cache vorbereitet und sollte bei Mehrinstanzen-Betrieb aktiviert werden.

Edge-Thinking: Potentielle Gamechanger Features

ECHTZEIT & UX

1. WebSockets / Socket.io Gateway (@nestjs/websockets)

Aktuell nutzen Direct Chats und Chatrooms HTTP-Polling oder reine Push-Notifications. Ein WebSocket Gateway ermöglicht instant Messaging, Tipp-Indikatoren ("schreibt gerade..."), Gelesen-Bestätigungen und Live-Anwesenheitsstatus.

🚀 Gewinn: Massiver Rückgang von HTTP-Request-Load, echte Chat-App Experience.
ARCHITEKTUR

2. Event-Driven Architecture (@nestjs/event-emitter)

Entkopplung von Seiteneffekten: Wenn ein Event oder Business erstellt wird, löst this.eventEmitter.emit('business.created', business) aus. Entkoppelte Listener übernehmen Push-Notifications, Statistiken und Cache-Invalidierung.

🚀 Gewinn: Maximale Wartbarkeit, einfache Erweiterbarkeit & sauberes Testing.
MOBILE PERFORMANCE

3. Aggregierter App-Bootstrap Endpunkt (GET /bootstrap)

Die Flutter-App führt beim Kaltstart 6–8 parallele Anfragen aus (Settings, Kategorien, Keywords, App-Version, Downtime, User-Profile). Ein einziger GET /bootstrap Endpunkt Bündelt diese Daten gecacht in einer Antwort.

🚀 Gewinn: Bis zu 70% schnellerer Flutter Cold-Start & reduzierte Mobilfunk-Latenz.
COMPLIANCE & GOVERNANCE

4. Admin Security Audit Trail Subsystem

Ein unmanipulierbarer Audit-Log für kritische Admin-Aktionen (Benutzer sperren, Partner löschen, Feature-Flags schalten, App-Versionen freigeben) mit Erfassung von Admin-ID, IP, Zeitstempel und Vorher/Nachher-Differenz.

🚀 Gewinn: Nachvollziehbarkeit, Datenschutz-Compliance & Sicherheit bei Team-Wachstum.

🔒 Security Hardening

UFW: nur 22, 80, 443. fail2ban für SSH. SSH-Key-only, kein Root-Login mit Passwort. Backend-Ports 3000/3100 nur auf 127.0.0.1 binden (-p 127.0.0.1:3000:3000).

0 € Aufwand: 2–4 h

Nutzen: Schließt größtes operatives Risiko. Kein Feature-Gewinn, aber Pflicht vor Skalierung.

💾 1–2 GB Swap aktivieren

Auf 1,8 GB RAM ohne Swap kann ein Memory-Spike (GC, Deploy, npm) zum OOM-Kill führen. Swap ist kein Performance-Booster, aber ein Crash-Preventer.

0 € Aufwand: 30 min

📦 Docker Compose statt docker run

docker-compose.yml existiert bereits im Repo. CI und Server auf Compose umstellen: reproduzierbare Config, ein Befehl für Restart, einfacheres Hinzufügen von Redis/Uptime-Kuma.

0 € Aufwand: 2–3 h

Empfohlene Roadmap

Kernaussage
Fazit
Docker ist für Nürnbergspots der richtige Default – nicht weil es das Beste ist, sondern weil Image, CI und VPS bereits darauf ausgerichtet sind. Ein Wechsel zu systemd, Podman oder Serverless bringt ohne klaren Trigger (Skalierung, Team-Wachstum, Compliance) mehr Migration-Risiko als Nutzen.

Der größte Hebel liegt nicht in der Container-Technologie, sondern in:
  1. Security Hardening (sofort)
  2. Deploy-Reliability (Zero-Downtime, Smoke Tests)
  3. Observability (Monitoring, Alerts)
  4. Langfristig: Cloud Run als Firebase-nativer Nachfolger des VPS

    2. Performance-Optimierungen

    2.1 Kritisch – Skalierung bei wachsenden Datenmengen

    Vollständige Collection-Reads ohne Pagination

    Mehrere Kern-Endpunkte laden alle Firestore-Dokumente und filtern teils im Speicher:

    EndpunktProblem
    GET /eventscollection('events').get() – kein limit, kein Cursor
    GET /businessescollection('businesses').get() – inkl. vollem customers[] pro Partner
    GET /special-pollsVollscan + Filter status / isHighlighted in Node
    getAllUserProfilesWithIds()Vollscan aller User – u. a. für Push-Notifications bei NEW_BUSINESS

    Empfehlung:

    1. Cursor-basierte Pagination (limit, startAfter, updatedAt/createdAt als Sortierfeld) für Listen-Endpunkte.

    2. List-DTOs ohne schwere Felder (customers, responses, große imageUrls-Arrays) – Detail-Endpunkt liefert Vollbild.

    3. Firestore-Queries statt In-Memory-Filter (where('status', '==', 'ACTIVE') wie bereits bei Curated Spots).

    4. Für Notifications: Topic-basiertes FCM oder Firestore-Query auf notificationPreferences.newBusinesses == true statt alle Profile zu laden.

    Impact: Weniger Firestore-Reads, kleinere JSON-Payloads, schnellere App-Starts (besonders Flutter Cold Start).

    Schwere Business-Listen

    GET /businesses liefert jeden Partner mit kompletter Scan-Historie (customers[]). Das wächst linear mit Nutzung.

    Empfehlung: Öffentliche Liste ohne customers; Partner-Portal-Endpunkt GET /businesses/:id/scans (paginiert) oder Nutzung von pass-scans (bereits unter users/{id}/pass-scans).

    Siehe auch: Tab Integrationen

    4. API-Design für bessere Client-Performance

    Diese Maßnahmen entlasten vor allem die Flutter-App (weniger Parsing, weniger Speicher, schnellere Screens).

    4.1 Aggregierter Bootstrap-Endpunkt

    Viele Screens brauchen beim Start: App-Settings, Kategorien, Keywords, Downtime-Status, ggf. App-Version.

    Vorschlag: GET /bootstrap oder GET /app-config liefert ein kompaktes Bundle (nur IDs + Namen + Flags). Reduziert 5–8 Roundtrips auf 1.

    4.2 Feld-Selektion

    Query-Parameter ?fields=id,name,logoUrl,categoryIds oder vordefinierte Views (?view=list vs ?view=detail).

    4.3 HTTP-Caching-Header

    Für selten ändernde Ressourcen (Legal Documents, Kategorien): Cache-Control: public, max-age=300 + ETag aus updatedAt.

    4.4 Kompression

    Express-Compression-Middleware (compression) für JSON > 1 KB – besonders bei Event-/Business-Listen.

    Client-Implementierungsanleitung: Direct-Chat Push-Notifications

    Diese Anleitung beschreibt, wie die Flutter/Dart Client-App die Push-Notification-Funktionalität für Direct-Chats integrieren kann.

    Übersicht

    Das Backend sendet automatisch Push-Notifications, wenn ein User eine neue Nachricht in einem Direct-Chat erhält. Der Client muss:

    1. FCM-Token beim Backend registrieren

    2. Push-Notifications empfangen und verarbeiten

    3. Navigation zu Chats bei Notification-Tap implementieren

    1. FCM-Token Registrierung

    1.1 Token vom Gerät abrufen

    Verwenden Sie Firebase Cloud Messaging, um den FCM-Token vom Gerät abzurufen:

    
import 'package:firebase_messaging/firebase_messaging.dart';

final FirebaseMessaging messaging = FirebaseMessaging.instance;

// Token abrufen
String? token = await messaging.getToken();

    1.2 Token beim Backend registrieren

    Registrieren Sie den Token beim Backend, sobald der User sich einloggt oder die App startet:

    Endpoint: POST /users/:userId/fcm-token

    Request Body:

    
{
  "token": "fcm-token-string",
  "deviceId": "unique-device-id",
  "platform": "ios" | "android" | "web"

    Beispiel-Implementierung:

    
Future<void> registerFcmToken(String userId, String token, String deviceId, String platform) async {
  final response = await http.post(
    Uri.parse('$baseUrl/users/$userId/fcm-token'),
    headers: {
      'Content-Type': 'application/json',
      'Authorization': 'Bearer $firebaseToken',
    },
    body: jsonEncode({
      'token': token,
      'deviceId': deviceId,
      'platform': platform,
    }),
  );
  
  if (response.statusCode != 201) {
    throw Exception('Failed to register FCM token');
  }
}

    Wichtig:

  • deviceId: Eindeutige Geräte-ID (z.B. mit device_info_plus Package)
  • platform: "ios", "android" oder "web"
  • Token sollte bei jedem App-Start aktualisiert werden (Token kann sich ändern)

    • 1.3 Token beim Logout entfernen

    Entfernen Sie den Token beim Logout:

    Endpoint: DELETE /users/:userId/fcm-token/:deviceId

    
Future<void> removeFcmToken(String userId, String deviceId) async {
  final response = await http.delete(
    Uri.parse('$baseUrl/users/$userId/fcm-token/$deviceId'),
    headers: {
      'Authorization': 'Bearer $firebaseToken',
    },
  );
  
  if (response.statusCode != 204) {
    throw Exception('Failed to remove FCM token');
  }
}

    2. Push-Notification Handling

    2.1 Notification-Handler implementieren

    Implementieren Sie Handler für Foreground- und Background-Notifications:

    
import 'package:firebase_messaging/firebase_messaging.dart';

// Foreground Notifications
FirebaseMessaging.onMessage.listen((RemoteMessage message) {
  print('Got a message whilst in the foreground!');
  print('Message data: ${message.data}');
  
  if (message.notification != null) {
    print('Message also contained a notification: ${message.notification}');
    // Zeige lokale Notification an
    _showLocalNotification(message);
  }
  
  // Verarbeite Notification Data
  _handleNotificationData(message.data);
});

// Background Notifications
@pragma('vm:entry-point')
Future<void> firebaseMessagingBackgroundHandler(RemoteMessage message) async {
  print('Handling a background message ${message.messageId}');
  _handleNotificationData(message.data);
}

void main() {
  FirebaseMessaging.onBackgroundMessage(firebaseMessagingBackgroundHandler);
  runApp(MyApp());
}

    2.2 Notification Data Parsing

    Die Notification enthält folgende Daten im data Feld:

    
void _handleNotificationData(Map<String, dynamic> data) {
  final type = data['type'];
  
  if (type == 'DIRECT_CHAT_MESSAGE') {
    final chatId = data['chatId'];
    final messageId = data['messageId'];
    final senderId = data['senderId'];
    
    // Navigiere zu Chat oder aktualisiere UI
    _navigateToChat(chatId);
  }
}

    Notification Data Struktur:

  • type: "DIRECT_CHAT_MESSAGE"
  • chatId: ID des Chats
  • messageId: ID der Nachricht
  • senderId: ID des Absenders

    • 2.3 Navigation zu Chat bei Notification-Tap

    Implementieren Sie Navigation, wenn der User auf die Notification tippt:

    
FirebaseMessaging.onMessageOpenedApp.listen((RemoteMessage message) {
  print('A new onMessageOpenedApp event was published!');
  _handleNotificationTap(message.data);
});

// Für Notifications, die die App geöffnet haben
Future<void> checkInitialMessage() async {
  RemoteMessage? initialMessage = await FirebaseMessaging.instance.getInitialMessage();
  
  if (initialMessage != null) {
    _handleNotificationTap(initialMessage.data);
  }
}

void _handleNotificationTap(Map<String, dynamic> data) {
  if (data['type'] == 'DIRECT_CHAT_MESSAGE') {
    final chatId = data['chatId'];
    // Navigiere zu Chat-Screen
    navigatorKey.currentState?.pushNamed(
      '/direct-chat',
      arguments: {'chatId': chatId},
    );
  }
}

    Zukunfts-Validierung

    Es werden nur Events importiert, deren Startdatum in der Zukunft liegt. Konkret:

  • Heute (14. Februar) = nur Events ab 15. Februar oder spaeter werden importiert
  • Events mit Startdatum heute oder in der Vergangenheit werden abgelehnt und erscheinen in results mit success: false und einer entsprechenden Fehlermeldung im field Startdatum

    • Duplikaterkennung

    Ein Event gilt als Duplikat, wenn beide Bedingungen erfuellt sind:

    1. Titel stimmt ueberein (case-insensitive, Whitespace normalisiert)

    2. Mindestens ein Datum aus den dailyTimeSlots stimmt ueberein

    Duplikate werden nicht erstellt, sondern als skipped markiert.

Future<String?> _bearer() async {
  final user = FirebaseAuth.instance.currentUser;
  if (user == null) return null;

}

Future<Map<String, dynamic>> _getJson(Uri uri) async {
  final token = await _bearer();
  if (token == null) {
    throw StateError('Nicht angemeldet');
  }
  final res = await http.get(
    uri,
    headers: {
      'Authorization': 'Bearer $token',
      'Accept': 'application/json',
    },
  );
  if (res.statusCode < 200 || res.statusCode >= 300) {
    throw Exception('GET $uri → ${res.statusCode}: ${res.body}');
  }
  final map = jsonDecode(res.body) as Map<String, dynamic>;
  return map;
}

Future<List<CuratedSpot>> searchCuratedSpots(
  String baseUrl, {
  String? namePrefix,
  List<String> keywordIds = const [],
}) async {
  final parts = <String>[];
  if (namePrefix != null && namePrefix.isNotEmpty) {
    parts.add('namePrefix=${Uri.encodeQueryComponent(namePrefix)}');
  }
  for (final id in keywordIds) {
    if (id.isNotEmpty) {
      parts.add('keywordIds=${Uri.encodeQueryComponent(id)}');
    }
  }
  final q = parts.isEmpty ? '' : '?${parts.join('&')}';
  final envelope = await _getJson(Uri.parse('$baseUrl/curated-spots/search$q'));

  return raw.map((e) => CuratedSpot.fromJson(e as Map<String, dynamic>)).toList();
}

import 'dart:convert';

    3. Admin-Bewertung setzen

    Regeln (wichtig für die UI)

  • Mehrfach änderbar: admin / super_admin dürfen adminRating per PATCH anpassen oder mit null wieder entfernen.
  • Idempotent: Sendet ihr im PATCH dieselbe Zahl wie bereits gespeichert (oder erneut null, wenn schon ohne Bewertung), ändert sich nichts (kein neuer adminRatedAt).
  • adminRatedAt nie mitsenden – setzt nur das Backend bei jeder inhaltlichen Änderung von adminRating.
  • Gültige Werte: Ganzzahl 1–5, oder null zum Entfernen (entspricht Backend-Validierung).

async function api<T>(path: string, init?: RequestInit): Promise<T> {
  const token = await firebaseAuth.currentUser?.getIdToken();
  if (!token) throw new Error('Nicht angemeldet');
  const res = await fetch(`${BASE_URL}${path}`, {
    ...init,
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${token}`,
      ...init?.headers,
    },
  });
  const json = (await res.json()) as { data: T };
  if (!res.ok) {
    throw new Error(`${res.status}: ${JSON.stringify(json)}`);
  }
  return json.data;
}

    Karten-Integration

  • Koordinaten: location.latitude, location.longitude für Marker
  • Marker-Tap: Detailansicht/Bottom Sheet mit title, description, imageUrl, prizeDescription, participantCount
  • Teilnahme-Button: Nur anzeigen, wenn Feature aktiv und Ei im Gültigkeitszeitraum

    • Geofencing (client-seitig)

    Die Nähe des Users wird nur im Client geprüft:

    1. User-Position via GPS holen

    2. Distanz zu location.latitude, location.longitude berechnen (z.B. Haversine)

    3. Teilnahme-Button nur anzeigen, wenn Distanz unter Schwellwert (z.B. 100 m)

    Das Backend prüft die Nähe nicht – es reicht, wenn der Client den Button nur bei ausreichender Nähe anzeigt.

  async createMessage(

    // NEU: Push-Notification an den anderen Teilnehmer senden
    const recipientId = chat.getOtherParticipantId(userId);
    if (recipientId) {
      await this.sendMessageNotification(recipientId, userName, dto.content, chatId, message.id);
    }
    
    return message;
  }

  private async sendMessageNotification(
    recipientId: string,
    senderName: string,
    content: string,
    chatId: string,
    messageId: string,
  ): Promise<void> {
    const truncatedContent = content.length > 100 
      ? content.substring(0, 97) + '...' 
      : content;

    await this.notificationService.sendToUser(recipientId, {
      title: senderName,
      body: truncatedContent,
      data: {
        type: 'DIRECT_CHAT_MESSAGE',
        chatId,
        messageId,
        senderId: recipientId,
      },
    });
  }
}
