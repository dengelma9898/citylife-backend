Quick Wins – hoher Nutzen, geringer Aufwand

Maßnahmen, die ohne Plattformwechsel den größten Hebel bieten. Referenz: docs/vps-server-inventory.md, .cursor/skills/vps-maintenance/

🔒 Security Hardening

UFW: nur 22, 80, 443. fail2ban für SSH. SSH-Key-only, kein Root-Login mit Passwort. Backend-Ports 3000/3100 nur auf 127.0.0.1 binden (-p 127.0.0.1:3000:3000).

0 € Aufwand: 2–4 h

Nutzen: Schließt größtes operatives Risiko. Kein Feature-Gewinn, aber Pflicht vor Skalierung.

💾 1–2 GB Swap aktivieren

Auf 1,8 GB RAM ohne Swap kann ein Memory-Spike (GC, Deploy, npm) zum OOM-Kill führen. Swap ist kein Performance-Booster, aber ein Crash-Preventer.

0 € Aufwand: 30 min

📦 Docker Compose statt docker run

docker-compose.yml existiert bereits im Repo. CI und Server auf Compose umstellen: reproduzierbare Config, ein Befehl für Restart, einfacheres Hinzufügen von Redis/Uptime-Kuma.

0 € Aufwand: 2–3 h

🔄 Zero-Downtime Deploy (Blue-Green)

Neuen Container starten (z. B. nuernbergspots-new auf Port 3101), Health-Check, nginx upstream umschalten, alten Container stoppen. Oder: Kamal / Watchtower mit Rolling-Strategie.

0 € Aufwand: 4–8 h

📡 Monitoring (Uptime Kuma)

Self-hosted auf dem VPS: HTTP-Checks für /health, /prd/health, Container-Status, Disk/RAM. Alerts per E-Mail, Telegram oder Pushover.

0 € Aufwand: 2–3 h

🏗️ CI: Build-Cache + GHCR

Docker Layer Cache in GitHub Actions (cache-from/cache-to). Optional Docker Hub → GitHub Container Registry (GHCR): keine Rate-Limits, Secrets bereits in GitHub.

0 € Aufwand: 1–2 h

✅ Post-Deploy Smoke Test

Nach SSH-Deploy in CI: curl -sf https://nuernbergspots.de/health und optional authentifizierter Bootstrap-Check. Rollback-Hinweis bei Fehler.

0 € Aufwand: 1 h

📜 Zentralisierte Logs

docker logs reicht für jetzt. Bei Wachstum: Loki + Grafana oder Papertrail/Logtail (Free Tier).

0–5 €/Mo Aufwand: variabel

Podman als Docker-Alternative (gleicher VPS)
Marginaler Nutzen
Podman ist Docker-kompatibel (gleiche Images, podman run), läuft rootless, kein Daemon.

ProContra
Rootless = weniger Angriffsfläche Migration-Aufwand, CI-Anpassung
Kein Docker-Daemon (weniger RAM) Compose-Support (podman-compose) weniger ausgereift
OCI-konform, gleiche Images Kein echter Kosten-/Feature-Gewinn vs. gehärtetes Docker

Empfehlung: Nur wenn Security-Hardening mit rootless Containern gewünscht – sonst Docker + UFW + localhost-Binding reicht.

🌐 Cloudflare als Edge-Layer

Proxy vor nginx: DDoS-Schutz, CDN für statische Assets, WAF, Bot-Management. Origin bleibt IONOS VPS. Free Tier für Basis-Features.

0 € (Pro: ~20 €/Mo)

🔥 Firebase App Hosting

Google's neues Hosting für Full-Stack mit Firebase. Primär für Web-Frontends; Backend-API-Support wächst. NestJS-Support prüfen – aktuell kein Standard-Pfad.

Pay-per-use

📱 Edge Functions (nur für Teile)

z. B. Bootstrap-Bundle, Location-Cache, Health am Edge – nicht der ganze NestJS-Stack. Hybrid: leichte Endpunkte am Edge, Rest auf VPS/Cloud Run.

variabel

🏗️ Separater Prod-VPS

Dev auf kleinem VPS, Prod auf separatem Server. Blast-Radius-Trennung, unabhängige Deploys. Doppelte Kosten, aber Prod isoliert von Dev-Experimenten.

~10–24 €/Mo

Empfohlene Roadmap

Kernaussage
Fazit
Docker ist für Nürnbergspots der richtige Default – nicht weil es das Beste ist, sondern weil Image, CI und VPS bereits darauf ausgerichtet sind. Ein Wechsel zu systemd, Podman oder Serverless bringt ohne klaren Trigger (Skalierung, Team-Wachstum, Compliance) mehr Migration-Risiko als Nutzen.

Der größte Hebel liegt nicht in der Container-Technologie, sondern in:
  1. Security Hardening (sofort)
  2. Deploy-Reliability (Zero-Downtime, Smoke Tests)
  3. Observability (Monitoring, Alerts)
  4. Langfristig: Cloud Run als Firebase-nativer Nachfolger des VPS
Phase 0
1–2 Tage
Security & Stabilität

UFW, fail2ban, SSH-Keys, Swap, Backend-Ports auf localhost, Docker Compose. Referenz: docs/vps-server-inventory.md

Phase 1
1 Woche
Deploy-Qualität

Post-Deploy Smoke Tests in CI, Uptime Kuma, CI Build-Cache. Optional: Blue-Green oder Kamal.

Phase 2
2–4 Wochen
Edge & Schutz

Cloudflare Proxy vor nginx. Secrets nicht im Image (.env.prd → Runtime). GHCR statt Docker Hub.

Phase 3
bei Bedarf
Skalierung

Redis (laut configuration-values.md), VPS-RAM-Upgrade oder Hetzner-Migration, Zero-Downtime als Standard.

Phase 4
langfristig
Plattform-Evaluation

Cloud Run PoC: gleiches Docker-Image deployen, Traffic-Vergleich, Kosten messen. Trigger: >10k MAU, Team ohne VPS-Ops-Kapazität, oder Compliance-Anforderungen.
